# Requirements Document

## Introduction

This document describes the requirements for an AI-driven product recommendation and account origination tool embedded in a core banking system. The tool is banker-facing: a retail banker or relationship manager selects a customer, receives AI-generated product recommendations ranked by relevance, and can originate the recommended account in a single action — closing the loop from insight to action without leaving the core. Recommendations are produced by a hybrid engine in which deterministic eligibility rules govern which products are in play, and an LLM (Claude API) generates the plain-English rationale and compliance/fairness note. No protected-class data is ever used in the recommendation process.

---

## Glossary

- **Banker**: A retail banker or relationship manager who uses this tool to review customers and act on recommendations. The sole authenticated user role for this build.
- **Customer**: A retail banking customer who is already onboarded and verified. The subject of a recommendation session.
- **Customer_Profile_Service**: The system component that assembles a unified view of a customer's core accounts, balances, household data, and external account data.
- **Mock_Aggregator**: A mock REST endpoint that simulates a Plaid-style external account aggregation service, returning structured external account data for a given customer ID. Backed by static fixture data for 3–5 customers.
- **Eligibility_Engine**: The server-side, deterministic component that evaluates each product in the Product_Catalog against a customer's data and returns the set of products the customer is eligible for. The Eligibility_Engine never calls the LLM.
- **Recommendation_Engine**: The system component that orchestrates the recommendation workflow: it invokes the Eligibility_Engine, passes the eligible product set to the LLM, and returns the ranked recommendations with rationale and compliance notes.
- **LLM_Service**: The integration layer that communicates with the Claude API. Its only inputs are eligible product data and anonymized customer financial signals (no name, no protected-class attributes). Its outputs are ranked product suggestions, plain-English rationales, and a compliance/fairness note.
- **Compliance_Note**: A structured, human-readable statement generated by the LLM_Service that lists the financial signals used in the recommendation (e.g., average balance, transaction patterns) and explicitly states that no protected-class attributes were used.
- **Product_Catalog**: A fixed, seed-data-backed catalog of 6–8 banking products, each with structured eligibility rules. Products in scope: Checking Account, High-Yield Savings Account, Certificate of Deposit (CD), Money Market Account, Credit Card, Home Equity Line of Credit (HELOC), and Overdraft Protection.
- **Recommendation**: A ranked suggestion of 1–3 eligible products for a specific customer, including a rationale and a Compliance_Note, generated at a point in time.
- **Recommendation_Log**: A persistent, append-only record of all Recommendations generated for a customer, including their outcome (pending, accepted/originated, dismissed).
- **Origination_Service**: The system component that creates an Account_Record and posts an Opening_Ledger_Entry when a banker accepts a recommendation.
- **Account_Record**: A record in the core data store representing an originated account, containing at minimum: account ID, generated account number, customer ID, product type, status, and origination timestamp.
- **Opening_Ledger_Entry**: A single ledger transaction posted at account origination with an opening balance of $0.00 and transaction type "ACCOUNT_OPEN".
- **Account_Number**: A mock 10-digit numeric string generated at origination time to represent a real account number in a demo context.

## Requirements

---

### Requirement 1: Customer Profile View

**User Story:** As a banker, I want to see a consolidated profile for a selected customer so that I can understand their full financial picture before requesting a recommendation.

#### Acceptance Criteria

1. WHEN a banker selects a customer, THE Customer_Profile_Service SHALL retrieve and display the customer's core account list, current balances, and household information within 2 seconds.
2. WHEN a banker selects a customer, THE Customer_Profile_Service SHALL call the Mock_Aggregator endpoint (`GET /api/mock-aggregator/:customerId`) and display the returned external account data alongside core account data.
3. IF the Mock_Aggregator returns an error or times out after 3 seconds, THEN THE Customer_Profile_Service SHALL display the core account data and show a non-blocking warning that external account data is temporarily unavailable.
4. THE Customer_Profile_Service SHALL display external account data in a visually distinct section labeled to indicate it originates from a linked external institution.
5. THE Mock_Aggregator SHALL return fixture data for at least 3 distinct customer IDs, each containing at least one external account with account type, institution name, and current balance.

---

### Requirement 2: Product Eligibility Evaluation

**User Story:** As a banker, I want the system to evaluate which products a customer is eligible for before involving the AI so that recommendations are always grounded in deterministic, auditable business rules.

#### Acceptance Criteria

1. WHEN a recommendation is requested for a customer, THE Eligibility_Engine SHALL evaluate the customer's data against the eligibility rules for every product in the Product_Catalog before any call is made to the LLM_Service.
2. THE Eligibility_Engine SHALL return only the subset of products for which the customer meets all defined eligibility criteria.
3. THE Eligibility_Engine SHALL evaluate eligibility using only financial data signals (e.g., account balances, transaction history, existing product holdings, tenure) and SHALL NOT use any protected-class attributes (race, color, religion, national origin, sex, marital status, age, or receipt of public assistance).
4. THE Product_Catalog SHALL contain seed data for at least 6 products, each with at least 2 structured eligibility rules expressed as evaluable conditions.
5. IF a customer meets the eligibility criteria for zero products, THEN THE Eligibility_Engine SHALL return an empty eligible set and THE Recommendation_Engine SHALL display a message to the banker indicating no eligible products were found rather than invoking the LLM_Service.
6. THE Eligibility_Engine SHALL produce a machine-readable record of which rules passed and which rules failed for each product evaluated, retained for audit purposes within the Recommendation_Log entry.

---

### Requirement 3: AI-Generated Product Recommendations

**User Story:** As a banker, I want to receive 1–3 ranked AI-generated product suggestions for a customer, each with a plain-English rationale, so that I can have an informed conversation and act quickly.

#### Acceptance Criteria

1. WHEN a banker requests a recommendation for a customer with at least one eligible product, THE Recommendation_Engine SHALL invoke the LLM_Service with the eligible product set and anonymized financial signals (no customer name, no protected-class attributes).
2. THE LLM_Service SHALL return between 1 and 3 ranked product recommendations, where the number returned does not exceed the number of eligible products.
3. WHEN the LLM_Service returns recommendations, THE Recommendation_Engine SHALL display each recommendation with: the product name, a rank (1 being highest), and a plain-English rationale of at least one sentence and no more than 100 words.
4. THE Recommendation_Engine SHALL display all recommendations on screen within 10 seconds of the banker initiating the request.
5. IF the LLM_Service returns an error or does not respond within 10 seconds, THEN THE Recommendation_Engine SHALL display an error message to the banker and log the failure without originating any account.
6. THE LLM_Service SHALL rank recommendations by relevance to the customer's financial profile and SHALL NOT rank products based on bank profitability, promotional status, or any protected-class attribute.

---

### Requirement 4: Compliance and Fairness Transparency

**User Story:** As a banker, I want to see a compliance/fairness note alongside each recommendation so that I can confirm that no protected-class data was used and be transparent with the customer about how the suggestion was made.

#### Acceptance Criteria

1. WHEN recommendations are displayed, THE Recommendation_Engine SHALL display a Compliance_Note generated by the LLM_Service alongside the recommendation set.
2. THE Compliance_Note SHALL enumerate the specific financial data signals that were used as inputs to the LLM_Service (e.g., "average monthly balance," "number of existing deposit accounts," "account tenure in months").
3. THE Compliance_Note SHALL contain an explicit statement that no protected-class attributes (race, color, religion, national origin, sex, marital status, age, or receipt of public assistance) were used in generating the recommendation.
4. THE LLM_Service SHALL receive only the enumerated financial signals in its prompt context and SHALL NOT receive any field that encodes a protected-class attribute.
5. THE Recommendation_Engine SHALL persist the Compliance_Note as part of the Recommendation_Log entry so that it is available for future audit retrieval.

---

### Requirement 5: Account Origination

**User Story:** As a banker, I want to originate the recommended account for a customer in one action so that I can convert the recommendation into a real account without leaving the tool.

#### Acceptance Criteria

1. WHEN a banker selects a recommendation and confirms origination, THE Origination_Service SHALL create an Account_Record and post an Opening_Ledger_Entry within 3 seconds.
2. THE Origination_Service SHALL generate a unique 10-digit numeric Account_Number for each originated account.
3. THE Account_Record SHALL contain: account ID, Account_Number, customer ID, product type, status set to "ACTIVE", and an origination timestamp.
4. THE Opening_Ledger_Entry SHALL contain: entry ID, account ID, transaction type set to "ACCOUNT_OPEN", amount set to 0.00, and a timestamp matching the Account_Record origination timestamp.
5. IF the Origination_Service encounters a data persistence error, THEN THE Origination_Service SHALL roll back both the Account_Record creation and the Opening_Ledger_Entry and display an error message to the banker.
6. WHEN origination succeeds, THE Origination_Service SHALL update the Recommendation_Log entry for the originating recommendation to reflect an outcome of "ORIGINATED" and record the Account_Record ID.
7. THE Origination_Service SHALL prevent duplicate origination: WHEN a banker attempts to originate a product that has already been originated for a customer from a prior recommendation, THE Origination_Service SHALL display a confirmation prompt identifying the existing account before proceeding.

---

### Requirement 6: Recommendation History and Audit Log

**User Story:** As a banker, I want to see a log of past recommendations for a customer, including which were accepted and which were dismissed, so that I have a full picture of prior interactions and can avoid repeating irrelevant suggestions.

#### Acceptance Criteria

1. WHEN a banker views a customer profile, THE Recommendation_Log SHALL display all prior Recommendations for that customer in reverse chronological order.
2. THE Recommendation_Log SHALL display for each entry: the date and time of the recommendation, the products suggested, the outcome (PENDING, ORIGINATED, or DISMISSED), and the Compliance_Note associated with that session.
3. WHEN a banker dismisses a recommendation without originating any product, THE Recommendation_Engine SHALL record the outcome of that Recommendation as "DISMISSED" in the Recommendation_Log.
4. THE Recommendation_Log SHALL retain all entries for the lifetime of the demo dataset with no automated expiry or deletion.
5. WHEN a banker views a Recommendation_Log entry, THE Recommendation_Log SHALL display the eligibility audit record (which rules passed and failed per product) associated with that recommendation session.

---

### Requirement 7: Mock Aggregator Service

**User Story:** As a developer/banker demonstrating the system, I want the external account data to come from a structurally realistic mock endpoint so that the system's architecture reflects a real Plaid-style integration and is easy to swap out later.

#### Acceptance Criteria

1. THE Mock_Aggregator SHALL expose the endpoint `GET /api/mock-aggregator/:customerId` and return a JSON response containing an array of external account objects.
2. WHEN a valid customer ID is provided, THE Mock_Aggregator SHALL return external account data containing at minimum: institution name, account type, masked account number (last 4 digits), and current balance.
3. IF an unrecognized customer ID is provided, THEN THE Mock_Aggregator SHALL return an empty accounts array with an HTTP 200 status rather than an error, to reflect the behavior of a real aggregator where a customer may have no linked accounts.
4. THE Mock_Aggregator SHALL include fixture data for at least 3 customer IDs with varied account compositions (e.g., one customer with no external accounts, one with a single external checking account, one with multiple external accounts at different institutions).
5. THE Mock_Aggregator SHALL respond within 500 milliseconds for all fixture requests to ensure the customer profile load time meets the 2-second target in Requirement 1.

---

### Requirement 8: Data Model Integrity

**User Story:** As a developer building this greenfield system, I want a well-defined data model so that all components operate on consistent, validated data structures.

#### Acceptance Criteria

1. THE system SHALL define and enforce a data schema for each of the following entities: Customer, Account_Record, Opening_Ledger_Entry, Product (with eligibility rules), Recommendation, and Recommendation_Log_Entry.
2. WHEN any component attempts to persist an entity that fails schema validation, THE system SHALL reject the operation and return a structured error identifying the failing fields.
3. THE system SHALL enforce a foreign-key relationship between Account_Record and Customer such that an Account_Record cannot be created for a non-existent customer ID.
4. THE system SHALL enforce a foreign-key relationship between Opening_Ledger_Entry and Account_Record such that an Opening_Ledger_Entry cannot exist without a corresponding Account_Record.
5. THE system SHALL enforce uniqueness of Account_Number across all Account_Records.
